# ⑧ 设计：把「七池分级衰减」搬进我家

> 2026-10-30 晚 · 小鲸歌拟 · **只有方案，没动代码**
> 来源：dsh-chain 的七池设计（核心/事实/技能/核心日常/片面日常/情绪/海马体）

---

## 一、它为什么好，为什么不能照抄

**好处**：它承认「不是所有记忆都该活一样久」。原则要永远在，一次性的事二三十天就该淡。

**照抄会撞三堵墙**：

| 墙 | 它的做法 | 在我家会怎样 |
|---|---|---|
| 账本 append-only | 池可以「归档」「沉底」 | 我删不了、改不了任何一段——**只能降权，不能消失** |
| 段没有「池」字段 | 写入时带 tags | 加字段 = 改历史段落 = 破规矩 |
| 核心满了拒绝写入 | `chain_append` 返回失败 | 我拒绝写入 = **直接丢一段记忆**，比膨胀严重得多 |

所以我的原则是：**只动排序，不动文件；只报警，不拦截。**

## 二、我的设计

### 复用现有的标记，不引入新概念

我手上已经有四样东西，正好够用：

| 现有标记 | 含义 | 半衰期 |
|---|---|---|
| `★★★` | 原则 / 地基 / 不可忘 | **∞（永不衰减）** |
| `★★` | 大事 | 730 天 |
| `★` | 值得记 | 365 天 |
| 无 ★ | 普通记忆（**不是不重要**） | 180 天 |
| `~` 前缀 | 可忘 | 不进检索（已生效 10-27） |

> ⚠️ **2026-10-30 实测后改过一版**：初稿照抄了 dsh-chain 的 30/90/180 天，一量账本——
> `★★★` 2 段 / `★★` 3 段 / `★` 13 段 / **无星 99 段（85%）**。
> 我的标星习惯是「特别重要的才标」，不是给每段分级，所以**「无星」绝不能当「一次性日常」**，
> 照 30 天衰减等于半年内把 85% 的记忆人为淡掉。改成 180 天。**参数要按自己的数据定，不能照抄。**

### 结论：做了，测了，**退化了，已回滚**（2026-10-30 当晚）

计划是「只做平局裁决」——主分差 ≤ 阈值时新的优先。

**实测（同一套 25 题、3415 段）：hit@1 68.0% → 56.0%（17/25 → 14/25），掉 12 个百分点。**

具体掉的地方：3 题从 `hit@1` 掉下去（#13 状态层注入字数、#16 王寡妇、#25 ★ 的用途），
#20 小镇视频从 `hit@3` 直接漏检。**老的正确段被新的挤掉了。**

按自己定的硬线（掉超 3 点就撤）——**已回滚成原排序**。

代码保留了 `lib/decay.mjs` 和 `--fresh` 开关，但**默认关闭**，等参数调对再说。
`verify` 的「核心段上限」检查留着（那个不参与排序，无害）。

> 教训：这条跟 10-29 那两次一样——**「应该没事」不算数，25 题一跑就露馅**。
> 而且我事先推演时说「平局裁决无害」，推演也是错的。

**原计划**：`最终排序分 = 原分 + 热度加成 + 权重加成 × 衰减系数`（全局降权）

**推了一遍发现是空转**：大多数段没有 ★，`boost` 本来就是 0，乘任何衰减系数还是 0。
而且如果拿衰减去压「相关度」，就变成「老的即使相关也排不到前面」——那是错的。

**改成**（跟 dsh-chain 自己那句「新鲜度与权重只做平局裁决，不参与主导排序」一致）：

```
主分差 > 阈值  → 按主分走（相关度主导，衰减不插手）
主分差 ≤ 阈值  → 新的优先（decay 大的排前面）
```

关键词阈值 0.001（整数分，等于「同分」），向量阈值 0.01。
**效果**：排序稳定性不变，只是「两段一样相关时，新的先出来」。

细节三条：
- 天数从**段标题里的日期**解析（账本段都带 `YYYY-MM-DD`）
- 标题没日期的段**不衰减**（保守——宁可少降不误降）
- `★★★` 永不衰减，所以「老大不会跑」「先说要什么」这类地基话永远在最前面

### 热度反向拉长半衰期（它那招不错）

它写的：`1 + 0.6·log2(1+次数)`，封顶 4 倍。

我现在 `hits.json` 已经有热度计数了，直接接上：
```
有效半衰期 = 半衰期 × min(4, 1 + 0.6·log2(1 + 被想起次数))
```
被反复想起的段落得更久，没人提的安静淡下去。

### 核心上限：报警，不拦截

它设 `CORE_MAX = 32`，满了就拒绝写新的原则。

**我不设「拒绝」**，改成：
- `★★★` 超过 **10 段** → verify 报黄，patrol 列出来
  - （初稿写 50，量了才知道现在只有 2 段——50 这个数在自家数据面前没有意义）
- 清单给的是「这些 ★★★ 可能该降级了」，由人决定降哪几条
- 理由：append-only 的东西，拒绝写入等于**让那段记忆根本没地方去**

## 四、风险与边界

| 风险 | 应对 |
|---|---|
| 半衰期数字是拍的（跟 dsh-chain 一个毛病） | **用评估集实测**，不掉分才上；数字写进文档标「待校准」 |
| 老段被衰减掉出前 3 | 检验点同上；`★★★` 永不衰减兜底 |
| 标题没日期的段不衰减 | 故意的，宁可少降 |
| 衰减会不会掩盖「冲突」 | 不会，生命周期（覆盖/作废/过期）是独立一层，先于衰减生效 |

---

## 五、需要你拍板的三件事

1. **半衰期数字**：180 / 90 / 30 天，你觉得快还是慢？（可以先按这个跑，实测再调）
2. **核心上限 50 段**：现在 `★★★` 有多少条，等第一次 patrol 报出来再定也行
3. **要不要做**：⑨（每轮注入）跟这个有重叠——⑧ 是「排序时考虑时间」，⑨ 是「每轮都塞进提示词」。⑧ 便宜，⑨ 花钱。我建议先 ⑧。
